# 195 件永禁出境文物 · 博物馆探索主线

> 国家文物局在 2002、2012、2013 年分三批发布《禁止出国（境）展览文物目录》，共 **195 件（组）**。
> 这是中国「最好的东西里，最不能再冒风险的那一批」——一级文物中的孤品与易损品。
>
> 📁 位置：`~/WorkBuddy AI/博物馆探索/`。原在 Obsidian 库里，2026-10-08 迁出独立成 WorkBuddy 工作区。

> 所有脚本的路径都相对**脚本自身**定位（不是写死绝对路径），整个工作区搬到哪都能跑。

**JSON 字段**：`id / name / era / cat / catMain / museum / city / province / batch / batchName / year / tags / reason / story / image / imageCredit / model / museumUrl / museumWechat`

**影像与 3D 字段**：
- `image`：实物照片 URL。来源 **Wikimedia Commons**（经 Wikidata `P18` 属性匹配），均为公有领域或 CC 授权
- `imageCredit`：署名信息 `{license, author, page, source, qid}`，卡片下方渲染成一行「📷 许可 · 作者」
- `model`：3D 模型 URL（glTF / GLB）。留空则不渲染 3D
- **前端三级回退**：`model` → `image` → **按材质类别绘制的内联 SVG 示意图**（11 类：青铜器 / 陶瓷 / 玉器 / 书画 / 漆木器 / 丝织刺绣 / 壁画石刻 / 金银器 / 文献杂项 / 画像砖 / 陶器）。加载失败会自动降级并记住降级结果
- 3D 用 Google `<model-viewer>`（约 1MB，**只在确实存在 `model` 数据时才按需加载**），点击缩略图可放大到 728×520 拖拽旋转
- **要加 3D 只需填 URL，不用改任何代码**
- 图片覆盖度：**42 / 195 件有实物照片**（约 22%），其余用类别示意图；全量查询已跑完，要再补跑：`sh tools/refresh_images.sh`

## 当本地软件用：双击启动器

**双击 `启动博物馆探索.command` 就行**，会在 `127.0.0.1:8765` 起一个只监听本机的静态服务并打开首页。关掉终端窗口就停。

### 为什么不直接双击 HTML

两种方式都实测过：

| | 双击 HTML（`file://`） | 走启动器（`http://127.0.0.1`） |
|---|---|---|
| 清单 / 搜索 / 筛选 | ✅ | ✅ |
| 勾选打卡 + 持久化 | ✅ | ✅ |
| 拍照打卡（IndexedDB） | ✅（Chrome 实测可用） | ✅ |
| 实物照片加载 | ✅ | ✅ |
| **杭州页地图** | ❌ **腾讯地图直接拒绝** | ✅ 正常 |

腾讯官方文档原话：**「不再支持 file:// 方式使用 Javascript API GL……配置完成后通过 localhost 进行调试使用」**。所以起本地服务不是为了好看，是地图能用的前提。

> 你的默认浏览器是 Chrome（`.html` 也指向 Chrome），所以双击打开时存储功能是好的。但如果哪天换成 Safari 打开，Safari 对 `file://` 的本地存储限制更严，打卡记录可能存不住——这也是建议走启动器的一个理由。

### 腾讯地图 Key（可选，但建议配）

页面里的地图**没有内置 Key**。没配的时候，地图区显示一块「地图未启用」的说明占位，**不是报错**——因为腾讯地图在没有 Key 时会自己弹一个「当前产品鉴权失败」的浮层，与其让你看到那个，不如直接说清楚怎么回事。

**没配 Key 会怎样**：地图区空着，但三家场馆的位置在下方图例里照样能看到，文物清单、打卡、照片、足迹统计**完全不受影响**。

申请是**免费**的，官方原话：**「目前Key申请完全免费，基础功能使用免费，且没有调用次数限制」**。

1. 打开 https://lbs.qq.com/ ，QQ 账号登录
2. 控制台 → 应用管理 → 我的应用 → 创建应用 → 添加 Key
3. JavaScript API GL **不需要勾选任何产品**，直接创建即可
4. 把 Key 粘进 `tmap-key.txt`（直接写 Key 本身，**不要**写 `TMAP_KEY=` 之类的前缀）
5. **双击 `重新构建.command`**，地图就启用了

### 启动器里踩过的坑

健康检查一开始用的 `curl`，结果**系统配了 `http_proxy` 时，curl 会把 `127.0.0.1` 也发给代理**，代理返回 502 但 curl 退出码仍是 0，脚本误判「服务已经在跑」直接退出——表现是双击后什么都没发生。改用 bash 内建的 `/dev/tcp` 探测端口，不经过任何代理。

### 要不要再打包成「真正的」桌面应用

现在这个形态（HTML + 启动器）已经能满足「本地自己看看 + 打卡记录」。再往上走有三个选项：

| 方案 | 体积 | 代价 | 什么时候值得 |
|---|---|---|---|
| **现状**：HTML + 启动器 | 约 500 KB | 无 | 够用。真的够用 |
| **Chrome「安装为应用」** | 0 | 点三下菜单 | 想要 Dock 图标和独立窗口。打开 `http://127.0.0.1:8765` → 右上角菜单 → 投放/保存和分享 → **安装页面为应用**。之后它就是个独立窗口的 App，不占额外体积、不用写一行代码 |
| **Tauri** | 3～10 MB | 要装 Rust 工具链 | 想要完全自包含（不依赖 python 起服务）、想要读写本地文件系统（比如直接导出照片到指定文件夹）、想分发给别人 |
| **Electron** | 150 MB+ | npm 一把梭 | 只在「已经很熟 Electron、且不在乎体积」时选。为一个个人工具不值 |

**建议**：先试 Chrome「安装为应用」，成本为零。真觉得不够（比如想要一键导出照片到磁盘、想要开机自动启动），再上 Tauri——这个项目的界面本来就是纯前端，迁 Tauri 主要是包一层壳。

**目前最该补的其实是「导出/导入」**：现在数据只活在浏览器里，清一次浏览器数据就全没了。这是本地应用最容易翻车的地方，比换技术栈重要得多。

## 为什么是这 195 件

**法律门槛**：《文物保护法实施条例》第四十九条——「一级文物中的孤品和易损品，禁止出境展览。」

**五类一律禁出的红线**：① 历代出土古尸 ② 宗教场所主尊造像 ③ 象牙、犀角质地文物 ④ 元以前书画、丝作品 ⑤ 宋元有代表性的孤品瓷器

**五条底层逻辑**：① 不可替代（孤品）② 脆弱易损（材质）③ 历史坐标（铭文证史）④ 文明源头（起源物证）⑤ 艺术巅峰（时代之最）

> 常见误解：「永禁」= 永久禁止**出境**展览，不是永久看不到。国内照常展出，偶尔参与国内巡展——这正是可以当作打卡主线的理由。

## 后续做小程序的几点建议

1. **数据层直接复用 JSON**，字段已经够用；`image` / `model` / `museumUrl` 已预留，建议再补 `lat/lng`（博物馆坐标）、`openHours`

3. **差异化点**：市面上讲国宝的很多，但**很少有人把「为什么它不能出境」讲清楚**。这个 `reason` 字段就是你的内容护城河
4. **合规注意**：**Wikimedia Commons 的公有领域 / CC 授权图可以直接用，只要保留署名**——这比抓各馆官网图省事得多（后者版权归各馆、多数还防盗链）。文字内容建议自己重写而非直接搬运。3D 模型同理，馆方合作的模型通常有使用范围约定
5. **冷启动**：先从杭州本地 7 件做起，做成「杭州国宝地图」，验证玩法后再铺全国

## 拍照打卡：照片只存在本机，不上传

两页都已支持。每张文物卡片底部有「📷 拍照打卡」按钮，**手机上点击会直接唤起相机**（`<input capture="environment">`），也能从相册多选。拍了照片**自动算作已打卡**，不用再单独勾一次。

**技术实现**：

| 环节 | 做法 |
|---|---|
| 存储 | **IndexedDB**（库 `guobao_photos_v1`，store `photos`，`relicId` 建索引）。照片是 Blob，不是 base64——base64 会让体积膨胀 33% 且撑爆 localStorage 配额 |
| 压缩 | Canvas 重绘，**长边压到 1400px、JPEG 质量 0.82、先铺白底**（否则 PNG 透明区变黑）。手机原图 3～5 MB → 压后约 300 KB |
| 展示 | 卡片内嵌缩略图条（缩略图 + 「＋」再加一张）｜「我的足迹」里的**照片墙**汇总全部照片 |
| 查看 | 灯箱：左右翻页、显示「文物名 · 第 n / m 张 · 拍摄时间」、可删除 |
| 降级 | 检测不到 IndexedDB（或隐私模式禁用）时，按钮自动置灰并说明原因，**打卡功能不受影响** |

**为什么不上传**：本地存 = 零服务器成本、零审核责任、零隐私风险。这版原型里用户照片**从不离开浏览器**，照片墙上写明了「全部只存在本机，不会上传」。

**两个页面数据是互通的**：

- **照片库共用**（都写 IndexedDB `guobao_photos_v1`）。文物 ID 两页是同一套（杭州 7 件的 ID 就是它们在 195 件里的真实 ID：12 / 13 / 14 / 15 / 136 / 151 / 172），所以在杭州页给玉琮王拍的照片，打开全国页也能看到
- **打卡状态共用**（localStorage `guobao_visited_v1`）。早先两页各存各的键（`museum195_visited_v1` / `hz_guobao_visited_v1`），导致「杭州页勾的打卡全国页不认」。已统一，并写了迁移逻辑把旧键数据合并过来、合并后删掉旧键（否则取消打卡后一刷新又会被迁移回来）
- 杭州页的照片墙和分享图**只统计杭州这 7 件**，不会把别的城市的照片混进来

**已知取舍**：换设备/换浏览器/清浏览器数据照片就没了。要跨设备同步，才需要后端——见下一节。

## 如果要上小程序：存用户照片到底贵不贵

**结论：存储本身很便宜，真正的成本不在存储。**

### 单价（2026 年公开价）

| 项目 | 价格 |
|---|---|
| 微信云开发 基础套餐 | **19.9 元/月**（原价 39）：20 万次调用 / 2 GB 容量 / 5 GB CDN 流量 / 2 GB 云函数出流量 |
| 云开发 超额容量 | **0.1 元/GB/日**（≈ 3 元/GB/月） |
| 云开发 超额调用 | 0.5 元/万次 |
| 云开发 CDN 流量 | **0.21 元/GB** |
| 腾讯云 COS 标准存储 | **0.118 元/GB/月**（比云开发便宜 25 倍） |
| COS 外网下行流量 | 0.5 元/GB |

### 算一笔账：1000 个活跃用户

假设人均 50 张、每张压到 300 KB：

- **容量**：1000 × 50 × 300 KB ≈ **15 GB**
- **云开发存储**：15 × 3 ≈ **45 元/月**
- **COS 存储**：15 × 0.118 ≈ **1.8 元/月**
- **流量**（假设每月每张被看 1 次）：15 GB × 0.21 ≈ **3 元/月**（云开发 CDN）

**存储+流量加起来，1000 用户也就每月几块到几十块。** 真正要花力气的是下面三件：

### 真正贵的地方

1. **内容审核是刚需，不是可选项。** 用户能上传图片 = 你能被用来传违规内容。微信要求 UGC 必须接入内容安全接口：`security.mediaCheckAsync`（免费，但有频率限制），**机器审核过了还得有人工兜底和举报处置流程**。这部分是运营成本，不是服务器成本。
2. **UGC 照片是你产品第一次背上真实的隐私与安全责任。** 用户可能拍到人脸、拍到同行的人、拍到位置信息。要做：上传前剥离 EXIF（**尤其是 GPS**）、隐私政策明示、可一键删除自己的数据、明确保留期限。做不好是真会出事的。
3. **CDN 流量是唯一可能失控的项。** 存储是线性慢增长，流量是**被浏览行为放大**的——一张照片被看 100 次就是 100 次流量。照片墙、排行榜这类"人人看人人"的功能最容易把流量打上去。

### 架构建议：本地缓存 + 云端归档两级

**微信小程序的本地文件上限只有 200 MB**（本地缓存文件 + 本地用户文件合计），所以不能全靠本地：

- **最近 N 张留在本地**（`wx.saveFile`），保证离线可看、打开秒开
- **原图归档到 COS**（0.118 元/GB/月，比云开发便宜得多），列表只拉缩略图
- **缩略图走 CDN + 长缓存**，原图按需拉取，别在列表页加载原图
- 容量用**生命周期规则**兜底：比如原图存 12 个月后转低频/删除，只留缩略图

> 一句话：**存照片这件事，钱不是问题，责任才是。** 如果只是"我自己记录一下"，那本地存储（现在这版）就是最优解；如果要让用户之间互相看见，才需要认真做后端 + 审核 + 隐私合规。

## 关于文物图片：现在是真照片 + 示意图混合

**结论：已经拿到实物照片，走的是 Wikimedia Commons。**

之前我判断「海外图库不可达」是**错的**——那是本机沙箱代理没把境外流量转发出去，不是网络问题。加上系统代理后 `commons.wikimedia.org` 正常返回。真正踩到的坑是：

- **Wikimedia API 对本机代理出口 IP 限流**（`You are making too many requests`），所以图片是**一批一批慢慢补的**，不是一次跑完（全量 195 件跑了一轮约 52 分钟）
- **中文名直接搜 Commons 很脏**（搜「良渚玉琮王」会返回一堆古籍 PDF 扫描件）。改用 **Wikidata 的 `P18` 属性**做中转：中文名 → Wikidata 实体 → 该实体登记的图片文件名。`P18` 是人工策展过的，精度高得多
- 后母戊鼎、曾侯乙编钟、越王勾践剑这些都能一次命中

**当前流水线**（`/tmp/rel195/wdpipe.py` → `wdall.py` → `repair.py` → `build.py`）：

1. `wbsearchentities`（中文优先，英文兜底）找 Wikidata 实体
2. 读该实体的 `P18` 拿到 Commons 文件名
3. 查 `imageinfo` 拿缩略图 URL + 许可 + 署名（署名走回退链，见下）
4. `repair.py` 二次补抓署名缺失的条目
5. 写进 JSON 的 `image` / `imageCredit`；**命中率约 3 成**（195 件里最终拿到 42 张；另有一些是名称对不上，已用归一化 + 子串匹配补回）

**缓存与重跑**：缓存落在 `/tmp/rel195/wd_cache.json`，已查过的不重复请求。全量查询已跑完（195 件全部有记录），要再补就跑：

```sh
sh /tmp/rel195/refresh_images.sh
```

**没匹配到的**（冷门文物、以及第二/三批里的书画）继续用**按材质类别画的 11 种内联 SVG 示意图**，卡片上标注「示意图 · 非实物照片」，不冒充真品。

**两道质量闸门**（宁可不出图，也不能张冠李戴 / 出糊图）：

1. **错配黑名单**：`build.py` 的 `BAD_MATCH`。例：搜「摇钱树」会命中 Wikidata 的 `Pteroceltis tatarinowii`（一种榆科树），必须拦掉
2. **长宽比闸门**：`MAX_ASPECT = 4.0`。卡片图片区固定 112px 高 + `object-fit: cover`，长卷书画塞进去会被放大裁切，**又糊又是随机一段**。例：清明上河图全卷 38414×1800（比 21:1），已自动退回类别示意图。想手动指定更好的图，填 `MANUAL_IMAGE` 字典即可

**署名回退链**：Commons 的 `Artist` 字段有时是空的，但 CC BY-SA 要求署名，不能留白。`wdpipe.commons_info` 按 **Artist → Attribution → Credit → 上传者** 依次回退，并记下来源（`authorSrc`），前端据此诚实标注身份——比如大克鼎显示「Meidosensei**（上传者）**」、墙盘显示「幽灵巴尼**（来源）**」。清理时顺带剥掉 `Credit` 字段里混入的时间戳和 "Own work" 之类的说明。

**当前覆盖度**：**42 / 195 有实物照片**（约 22%），其余 153 件用类别示意图。42 张全部有许可信息、全部有署名、实测 100% 加载成功。全量查询已跑完（缓存 199 条），剩下的确实拿不到——冷门文物（如「朱然墓出土贵族生活图漆盘」「常阳太尊石像」）在 Wikidata 上没有 `P18`，第二三批书画更是重灾区。

**版权**：只取公有领域或 CC 授权图，每张卡片下方标注「许可 · 作者」，链接回 Commons 文件页。这比抓各馆官网图安全得多。

## 关于加 3D 视图：方便，而且已经铺好了

**结论：方便。** 代码侧和资源侧都已经验证过：

- **代码侧**：`model` 字段已预留，三级回退（`model` → `image` → 类别示意图）已实现，`<model-viewer>` 只在真有 3D 数据时才加载。实测塞一个 `.glb` 进去，缩略图立刻变成可旋转 3D，点击放大到 728×520 正常渲染（关闭时释放 WebGL 上下文）
- **依赖侧**：`model-viewer`（unpkg / jsDelivr）与 `three.js`（cdnjs）均返回 200，CDN 可用
- **真正的难点不在代码，在模型数据**：这 195 件的**权威 3D 扫描基本没有公开**。故宫「数字文物库」等有部分 3D 展示，但多为网页内嵌、不提供可下载的 `.glb`；想拿高精度模型基本要走馆方合作
- **现实路径**：① 先挑 1～2 件做原型（比如浙博之江馆的玉琮王），别一上来铺 195 件 ② 模型放外部托管（每个 `.glb` 通常 5～50 MB，塞进单文件 HTML 不现实）③ 手机 photogrammetry（Polycam / RealityScan）只能拍复制品或文创，真品不让拍
- **技术选型建议**：只是「转着看一件文物」→ `<model-viewer>` 足够，比 Three.js 省得多；要**把文物放回场景里**（玉琮放回良渚祭坛、编钟放回曾侯乙墓室）才需要 Three.js 做场景合成
